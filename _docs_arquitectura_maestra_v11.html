Documento Maestro de Arquitectura — v11

Reemplaza la versión 10.0. Cada afirmación de este documento fue verificada directamente contra el código y la base de datos en producción — no contra la especificación original.

Estado: en operación, verificado 2026-07-24 Base de datos: PostgreSQL / Supabase Despliegue: Railway (backend) + Render (frontend)

00Resumen ejecutivo

RadFor-360 es una plataforma SaaS de dos pilares — Radar (rastreo de convocatorias de financiación) y Formulador (estructuración de proyectos con IA) — con un pipeline de auditoría financiera en Pesos Colombianos construido y probado sobre datos reales. Este documento reemplaza la v10.0, que describía una migración a Firebase y un motor de búsqueda que no existen en el código real.

01Fe de erratas — qué cambió respecto a la v10.0

La v10.0 describía un estado aspiracional. Estas son las diferencias verificadas contra el código real:

Afirmación en v10.0Estado real verificado
"Migrado a Firebase (Firestore y Auth), eliminando PostgreSQL y JWT manual"falso — no existe ninguna referencia a Firebase/Firestore en el backend. La base de datos es PostgreSQL vía Supabase; la autenticación es JWT propio firmado con JWT_SECRET.
"Caché 24h vía Firebase/Redis"falso — tokenBlacklist.js declara explícitamente "Sin Redis. Sin dependencias externas."
"Motor unificado en Gemini 1.5 con Google Search Grounding (reemplaza Perplexity, Tavily y Claude)"falso — no hay ninguna referencia a Perplexity, Tavily ni Search Grounding. El Radar rastrea entidades reales vía EntityScraper.js + CronScheduler.js (ver sección Radar).
"Despliegue en contenedores Docker orquestado para alta disponibilidad"parcial — sí existen Dockerfile.backend/Dockerfile.frontend, usados por Railway/Render como mecanismo de build. No hay una capa de orquestación propia (Kubernetes/Swarm) — son plataformas PaaS gestionadas.
"Consolidado a una única variable GEMINI_API_KEY"impreciso — la variable real es GOOGLE_API_KEY, usada en 8 módulos distintos de IA. No está mal la intención (una sola clave de IA), pero el nombre no coincide.
RBAC (access_radar / access_formulador), aislamiento por org_id, hash de versión finalconfirmado — coincide con el código real (user_subscriptions, middleware requireAccess(), project_version_hashes).
Añadido en esta versión: el pipeline de auditoría financiera (Sprints 1–4, ver sección "Pipeline de 4 motores") no existía en la v10.0 — se construyó, probó con datos reales y verificó en esta sesión.

02Stack tecnológico real

Frontend

  • React + TypeScript + Vite, servido en el puerto 5173 vía pm2 (radar-frontend).
  • Code-splitting con React.lazy() para las ~25 páginas del ecosistema — reduce el bundle inicial.
  • Diseño calcado desde Stitch MCP para pantallas específicas (marcadas explícitamente en el código con comentario "Calco estricto Stitch"); el resto son páginas construidas directamente en código.

Backend

  • Node.js/Express, puerto 8000 vía pm2 (radar-backend), módulos ES (import/export) en todo el codebase.
  • Motor de base de datos con 3 capas de resiliencia (database.config.js): pool directo (Capa 1) → REST de Supabase con service_role (Capa 2, la que opera hoy) → degradación controlada (Capa 3).

Base de datos

  • PostgreSQL gestionado por Supabase, extensión pgvector con índices HNSW para búsqueda semántica (columnas vector(768)).
  • Row Level Security habilitada en las 31 tablas públicas. Nota honesta: las políticas RLS son un blindaje secundario — el backend siempre opera con la llave service_role, que bypasea RLS por diseño. El aislamiento real ocurre en cada ruta vía WHERE org_id = req.userId.
  • proyectos.id y project_anexos.id son TEXT (no UUID) — heredado del bootstrap original de server.js; toda tabla nueva respeta ese tipo para poder referenciarlas.

Despliegue

  • Backend → Railway, vía Dockerfile.backend + railway.json.
  • Frontend → Render, vía Dockerfile.frontend + render.yaml.
  • Almacenamiento de archivos → Supabase Storage (bucket privado anexos), no disco local — Railway reconstruye el contenedor en cada deploy, así que cualquier archivo en disco se perdería.

05Suscripciones y control de acceso (RBAC)

Confirmado exacto contra el código real. Tabla user_subscriptions con columnas access_radar / access_formulador (booleanas). Middleware requireAccess(modulo) en el backend valida el permiso en cada ruta protegida; en el frontend, el componente PlanGate replica la misma lógica para no renderizar módulos sin acceso.

  • Suscripción Radar → habilita Rastreo 1/2 + Directorio + Favoritos.
  • Suscripción Formulador → habilita M3–M12 completos, incluida ingesta manual de pliegos propios.
  • Plan Suite → ambos, más el puente M2 sin restricciones.
  • Un usuario con solo Radar que intenta cruzar el puente es redirigido al panel de Planes; el botón valida el permiso antes de inyectar datos en el Formulador.

07Relaciones entre módulos

  • Radar → Formulador: el Puente (M2) transfiere la convocatoria seleccionada como semilla de un nuevo proyecto en el Formulador — el usuario necesita el plan Suite o cambiar de plan para completar el cruce.
  • Anexos → Pipeline financiero: solo un anexo subido con categoria = presupuesto_apu y extensión .xlsx/.xls dispara ExtractorService.js → AuditorForenseService.js en cadena; cualquier otra categoría de anexo (legal, técnico, institucional) se guarda igual pero no entra al pipeline.
  • Pipeline financiero → Ficha Técnica Maestra: los hallazgos de project_hallazgos y las métricas de project_escenarios_estres/project_sroi_metrics están disponibles para el Reporte/Ficha Técnica final, pero su inclusión visual en ese reporte es un paso de frontend aún no verificado en esta sesión.
  • Suscripciones → todo: requireAccess() es el único punto de verdad — tanto el Radar como cada endpoint del Formulador lo consultan antes de ejecutar cualquier lógica de negocio.
  • Auth → Suscripciones: al iniciar sesión, /api/auth/verify devuelve el plan y los flags access_radar/access_formulador en el mismo payload — el frontend no hace una segunda llamada para saber qué puede mostrar.

08Pipeline de auditoría financiera — 4 motores (nuevo)

Esta capa no existía en la v10.0. Construida, probada con datos reales end-to-end, y documentada en detalle esta sesión.

Motor 1 · automático
ExtractorService.js
Excel → project_apu_lineas, en COP, idempotente
Motor 2 · automático
AuditorForenseService.js
HSEQ ausente + descuadres aritméticos
Motor 3 · deliberado
EstresadoFinancieroService.js
Choque macroeconómico, VIABLE/RIESGO/CRITICO
Motor 4 · deliberado
ValorExponencialService.js
SROI (ratio explícito) + mapeo ODS
Principio de diseño no negociable: ningún motor fabrica una cifra financiera ni una cita legal. El etiquetado HSEQ es una alerta técnica, no un dictamen; el % de choque y el ratio SROI los define el formulador explícitamente — nunca un valor "estándar" inventado. El único número externo usado es el SMMLV 2026 real ($1.750.905 COP, Decretos 1469/1470 de 2025).

10Radar — motor de rastreo real

No usa Perplexity, Tavily ni Gemini Search Grounding. Es scraping directo y estructurado:

  • EntityScraper.js visita las páginas de convocatorias de cada entidad ya validada en el Directorio.
  • DataIngestor.js normaliza lo extraído antes de insertarlo.
  • sectorClassifier.js usa GOOGLE_API_KEY (Gemini) solo para clasificar sector, no para buscar.
  • CronScheduler.js orquesta la periodicidad (Rastreo 2 → Rastreo 1 → backup).

11Autenticación

  • Login/registro propios en server.js: contraseña con pbkdf2 (100.000 iteraciones, sha512), token JWT HS256 firmado con JWT_SECRET, expiración 7 días.
  • auth.middleware.js valida primero contra Supabase Auth si está configurado; si falla, cae a la verificación JWT local — necesario porque el login propio nunca emite sesiones reales de Supabase Auth.
  • Aprobación manual de registros (nuevo): todo registro nuevo queda con is_approved = 0 — no puede iniciar sesión hasta que un administrador lo apruebe desde /admin/usuarios-pendientes. Se dispara un correo de aviso al administrador vía Brevo.
  • Modo Visitante: token temporal de 24h (/api/auth/trial), limitado a 3 tokens/hora por IP.
  • Rate limiting estricto en /api/auth/*: 5 intentos fallidos por 15 minutos por IP (contador en memoria, se reinicia con el proceso).

13Deuda técnica real (no está en ninguna versión anterior)

  • Envío de correo transaccional depende de credenciales de Brevo — configuradas parcialmente en esta sesión; Resend (usado por el flujo de Stripe) sigue sin configurar.
  • Stripe (cobros reales) sin credenciales de producción.
  • Páginas de Términos/Privacidad tienen campos entre corchetes (razón social, NIT) pendientes de completar con datos reales de la empresa, y requieren revisión legal antes de publicarse.
  • El módulo de exportación a formatos MGA/BID/OXI genera documentos basados en la estructura oficial, no son los formularios descargables exactos del gobierno.
